- **CR064 — [Forecast: the annual close, the assumptions key, and the module form](../cr/cr-064-forecast-annual-close-and-assumptions.md)** — *🟡 IN-PROGRESS · v3 · P0/P1/P3 built and gate-verified (731 backend / 298 frontend, six ratchets, lint 0 errors); **nothing deployed**; migration **052** pending on dev and prod.* Started as one question — *we customised the module form for Loan, should the other types get the same treatment?* The answer is **no**, and the reasoning is the CR's §5: `module_type` is a free-text list the owner edits (prod carries both `Asset` and `asset`), and `fcModulePayload` sends every field on every save — so a type-gated form **hides** a live value rather than clearing it, which is why CR062's Loan carve-out needed a preview endpoint and a confirmed delete *per type*. Looking for the answer turned up three defects instead.
  - **P0 (built) — the editor computed foreign-currency USD at FX = 1.** `resolveFxRate` read `Rates.USDPLN`/`Rates.USDEUR`; the live document spells them `{PLN, EUR}` (the engine and FCExpSetup both read `PLN ?? USDPLN` — this was the one reader that did not), so it found nothing, returned **1**, and then **multiplied** by it where the engine **divides**. An unmatched €390,000 property posts **$390,000** instead of ~$453,000, and since `fcbuilder-module.js` seeds the USD series from the stored column and `index.js:833` derives the module's FX from the ratio, it also reports an implied rate of **1.0** into the FX-effect attribution — and the sync effect **overwrites** a correct hand-typed figure with it. Latent only because all ten live non-USD modules are matched (that branch uses the ledger's own ratio); the module the owner had open when this started was an unmatched **EUR** one. Extracted to `utils/fcModuleFx.js` with 15 tests, including one that asserts the *other two* readers still accept both spellings so the gap cannot reopen from the other side.
  - **P1 (built, migration 052) — a rename strands a scenario's assumptions.** Period, inflation, FX and tax live in `forecast_assumptions` keyed by scenario **NAME**; `PUT /scenarios/:id` renamed the row and nothing else. The failure is not the loud one it looks like: generate throws once, the owner saves Forecast Settings to clear it, that write refreshes only `scenarios` from the DB names, and generate then **succeeds** with an empty inflation list — `buildRates` seeds `entries[0]?.Rate ?? 0`, so **0% inflation for 36 years, silently** (the CR045 §1 / CR048 class). Prod carries **five** dead names from renames that already happened. `renameScenario` now does both in one transaction and `updateScenario` **throws** on a name so no caller can bypass it; 052 prunes the orphans, **refusing** when they sit alongside a live scenario with no inflation entry of its own — the shape of a rename, where pruning would destroy live assumptions (falsified on a prod copy). *The id-stamping design was drafted and rejected*: `syncAssumptions`'s `rekey` would have carried the **base's** id onto every variant row (reintroducing the same 0%-inflation bug), and the override differ strips `{Scenario, id}` but not `ScenarioId`, so every variant would report a phantom `inflation`/`FX` override — the CR050 v3.0.110–112 class.
  - **P3 (built) — the form, without touching type.** A section collapses to a `+ Add …` line when every field in it is blank or zero, and opens the moment anything is set: it **cannot hide a live value by construction**, so it needs no confirm, no preview and no delete path, and it works for all nine types plus the tenth the owner invents next. Tax is **0-for-103 modules**; Real Estate never uses Income (0 of 40), Business never Expenses (0 of 18), Liability and Asset use neither. Per-type **labels** only (Private Equity → *Capital Call* / *Distribution*, Fixed Income → *Coupon Spread*), where a lookup miss costs a noun rather than a value. **And the blank-row question is answered by disproving its premise:** the two nameless prod modules are not Cancel's doing — CR042 made New Module a client-side draft in `11fc3b5` on 2026-07-13 and both rows were written on 2026-07-14 — they are **Generate**'s, which saves the draft before it builds. `assertModuleBody` now refuses a module with neither an account nor a name (one guard, every write path), so **Cancel needs no change at all**. §4.4 was withdrawn on inspection: setup status is already a column, an inline `select` and a filter.
  - **P2 (designed, needs an owner decision, NOT built) — the annual close.** Every module in all five scenarios is anchored at **2025-12-31** while every scenario runs `PeriodStart = 2027`, so each carries **two base years at once** and the module anchor is **a year behind the scenario's own**. `crud.refreshModulesFromActuals` already re-bases a whole scenario from the ledger and is wired to the copy-scenario modal — what it does not do is move `PeriodStart` with the anchor, offer market value for non-loans (correct as a default, wrong as the only option: for the four Fidelity accounts the ledger balance *is* market value), preview anything, or run in place. The open question is whether the year rolls **in place** on one long-lived scenario or keeps **minting a copy** — a question about how the owner works, not one the code can settle.
  - **P4 / P5 (designed, not scheduled):** plan-vs-actual for the live year; sensitivity runs on CR053's existing scratch harness.
  - **P6 (built, migration 055) — income a business can express.** Owner: *"there is no way to change how this grows relative to inflation — only the yield adjustment, which is not relevant to a business."* True, and the cause was worse: **the typed amount was not being used at all.** Income has two mutually exclusive modes and the yield wins on a **single** row, discarding `income_amount` — and **all six income-bearing modules in prod are in yield mode**, so all six had a dead Income Amount. United Beverages: **192,266 PLN typed** while the engine books **77,163 USD** for 2027 = `avg(3,846,154 / 3,870,192) × (2.5% − 0.5%)`, to the dollar. - **CR063 — [Chart of Accounts ordering (and the dropdowns that read it)](../cr/cr-063-coa-ordering.md)** — *✅ COMPLETE · v3 · **shipped as v3.10.0 (2026-07-31)**, migration **049** on dev and prod.* Four owner requests on one page, and the third turned out to expose a structural gap. **The order of the Chart of Accounts is nobody's decision.** `accounts.display_order` has been in the schema since the seed and `findAll`/`getChildren`/`getBalances` all order by it — but `getTree()`, the one path every tree, report and dropdown actually goes through, **selects it and then sorts `ORDER BY path`, where `path` is `ARRAY[id]`**. So the COA page, Balance Sheet, Cash Flow, the budget worksheet and the forecast account list all render in **insertion order**. It looks deliberate only because the original seed inserted rows in a sensible order. It also cannot simply be switched on: the column is a **global** 0–207 sequence, not a rank within the parent, and `create()` hard-codes **0**, so 22 accounts share that value and — measured on dev — **68 of 229 rows would move** the moment the sort started honouring it, in three reports and not just on the COA page.
  - **P0 (built, verified in a browser):** *Analyze PS Data* removed — PS is no longer a data source — and with it the 115-line handler, the results banner, the **quick-add missing accounts/categories** path that consumed its output (including the add-modal branch that fired `sync-to-transactions` and re-ran the analysis) and the three now-dead `quickadd` modes in `COAEditModal`. **The backend `/ingest-ps/analyze-ps` endpoint stays** — `UploadPS.jsx` calls it too, and "Upload PS: keep" is a standing CR042 decision. The tree gained the reports' four expand/collapse controls (all + one-layer, both directions), on the shared button primitive rather than a page-local class — the button-CSS guard rejected the bespoke one. Proven by clicking, since neither half is visible to a unit test: 231 rows → collapse all → **2** → +1 level → **8** → **34** → −1 level → **8** → expand all → **231**, each button disabling at its own extreme, no console errors.
  - **P1:** migration **049** rewrites `display_order` as a per-parent rank, ranked by **today's visible order (`id`)** rather than by the existing value — ranking by the existing value would bake the 68-row reshuffle in instead of preventing it. The success criterion is that **nothing moves**: the migration and the `getTree` flip (`ARRAY[display_order, id]`, the form already used in `ingestPs.js`) ship together, verified by diffing Balance Sheet / Cash Flow / budget worksheet before and after. `create()` then **appends** (`MAX(sibling)+1`) instead of prepending — which is the real fix for the complaint that opened this, a new account landing somewhere arbitrary. Plus `POST /coa/reorder` taking the **whole sibling list**, not a direction: idempotent, single transaction, and able to reject a stale client whose id set no longer matches.
  - **P2:** ↑/↓ buttons in the existing row-action cluster (owner's choice over drag-and-drop — no dependency is installed, and it keeps keyboard access), disabled at the first/last sibling and **disabled entirely while a search or filter is active**, because in a filtered view the row above is not the sibling it would swap with.
  - **Built, and one sequencing error worth keeping:** half of P3 belonged in P1. `findAll` and `getBalances` were already sorting `ORDER BY a.display_order, a.name` — on the **global** sequence — so making the column a per-parent rank does not leave them unchanged, it **breaks** them (every parent's rank-1 child first, then every rank-2). The parity run caught it in seconds (`/accounts?leafOnly=true` came back scrambled while the trees were fine), and a shared `SORT_PATH_CTE` now serves all four flat-list readers. *A rank scoped to a parent silently breaks every consumer that treated the column as global* — found by diffing responses, not by reading. **Parity holds:** `reports/balance`, `reports/cash-flow`, `budget/cash-flow` and `budget/category-groups` byte-identical across the migration; both COA trees identical in name sequence. 10 new backend tests (704 total) and 9 new frontend, with the ordering claims **falsified first** — reverting the sort flip and the append default turns 3 red, reverting `findPLeaves` a 4th, and restoring `useCoa`'s sorts turns the frontend assertion red (its fixture had to be changed to make that possible: the old tree was alphabetical, so it could not tell COA order from a `.sort()`). Clicked end to end: an arrow moves a category, ends disable, a search disables every arrow, and reordering on the COA page changes the **forecast New Module → Account** dropdown with no reload.
  - **P3:** the three alphabetical `.sort()`s in `useCoa` come out — including `bsLevel2Options`, added **2026-07-31** precisely because tree order buried a new category, and explicitly released by the owner now that the order is theirs to set — and the two flat list endpoints (`findPLeaves`, `GET /accounts/categories`, both `ORDER BY a.name`) learn the tree rank via the same recursive CTE.

<a id="promote-cutoff-ui"></a>
- **Make the bank-feed promote cutoff an explicit choice at mapping time** — *🔧 small, unblocked, real risk reduction.* `account_source_mappings.promote_from_date` is **read-only everywhere in the frontend** (help text + the diagnostic page; no API write path), so today mapping an account means "promote its entire staged history" and there is no way to say otherwise. That is exactly what turned the 2026-07-14 Black Card mapping into **31 duplicate transactions** — $8.4K gross but net only +$267, so a balance check could not see it. Migration 043 (2026-07-30) pinned the two live NULL cutoffs and `setBankFeedMapping` now pins one whenever an account is mapped, which blocks a *later*-arriving older row — **but it does not close this class**, because the Black Card duplicates were already staged at the moment of mapping. Closing it needs a date field on the mapping UI plus a write path, so the owner states the cutoff deliberately when adopting a feed account.

<a id="promote-currency-guard"></a>
- **Refuse to promote a staged row whose currency disagrees with the target account** — *🔧 small, unblocked, general form of a fix we just made specifically.* Nothing in the promote path checks that a `bankfeed_staging` row's currency matches `accounts.currency`, so a mis-attributed row books a foreign amount into an account as if it were native — and **no balance check can see it**, which is the same invisibility that let the Black Card incident survive review. This is not hypothetical: fintable serves four Revolut **EUR** transactions under a wallet it labels **"(USD)"** ([CR059 §18](../cr/cr-059-fintable-api-ingestion.md)), and on the Sheet path two of them were promoted onto Revolut-USD before bank-feed `6d108ec` fixed the converter. Migration **050** closed that one path by making the mapping ignore-only, but the class is open for every other account: any upstream re-attribution, re-consent or shared-name collision can reproduce it. A guard costs one comparison at promote time; the design question is whether a mismatch should **block** the row (safe, but a legitimately multi-currency feed account stops promoting) or **flag** it for review on the reconcile page. Related: [the promote-cutoff write path](#promote-cutoff-ui) — both are "the mapping should state its assumptions rather than infer them".
